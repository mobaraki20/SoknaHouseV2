# قرارداد ساده‌سازی محصول Sokna House

این سند معیار دائمی Microcopy و سادگی عملیاتی House است و باید همراه `FAMILY_ENGINEERING_STANDARDS_FA.md` رعایت شود. مقیاس مرجع: حداکثر حدود ۲۹ مهمان و ۳ نیروی اجرایی.

## ۱. زبان رابط

- کاربر نباید برای فهم یک گزینه اصطلاح معماری نرم‌افزار بداند.
- نام‌های عملیاتی ترجیح دارند: «وضعیت سامانه»، «پشتیبان و بازیابی»، «امکانات اختیاری»، «ووچر مهمان».
- Schema version، Timezone، Tracking و Maintenance جزئیات فنی‌اند و به‌صورت Progressive Disclosure نمایش داده می‌شوند.
- متن خطا برای کاربر انسانی و کوتاه است؛ متن خام فنی فقط در Log می‌ماند.

## ۲. File Input

- Chrome خام مرورگر مانند `Choose File / No file chosen` در رابط فارسی نمایش داده نمی‌شود.
- Component مشترک File Picker استفاده می‌شود. Native `<input type=file>` Source of Truth باقی می‌ماند.
- این قرارداد برای لوگو، مهر، تصویر اتاق، Backup، Update و نصب دستی فونت یکسان است.

## ۳. فونت

- UI و Voucher باید Vazirmatn را درخواست کنند.
- مدیر باید در «وضعیت سامانه» بتواند آماده‌بودن فونت را ببیند، دریافت خودکار را Retry کند یا فایل معتبر WOFF2 را Local نصب کند.
- Release فایل فونت باینری توزیع نمی‌کند.

## ۴. ووچر

- Action پرونده «ووچر مهمان» است، نه «چاپ ووچر».
- دانلود PDF، ارسال/اشتراک و چاپ باید بدون حدس‌زدن مسیر قابل مشاهده باشند.
- A5 و Receipt ترکیب‌بندی مستقل دارند؛ PDF نمونه A5 نباید به‌خاطر Padding یک صفحه سفید دوم بسازد.

## ۵. Backup و Update

- «پشتیبان و بازیابی» بین دانلود Backup داده و برگرداندن اطلاعات تفکیک روشن دارد.
- Update UI فقط فایل، نسخه جاری، وضعیت نصب و در صورت وجود Snapshot معتبر «بازگشت به نسخه قبلی» را برجسته می‌کند.
- History و جزئیات فنی به‌صورت بسته/Secondary نمایش داده می‌شوند.

## ۶. Definition of Done

هر تغییر در این حوزه باید حداقل این Gateها را پاس کند:

```bash
php tools/product_simplification_contract_check.php
php tools/ui_contract_check.php
php tools/code_hygiene_check.php
python tools/voucher_browser_contract_check.py
```

## لیست انتظار
- Action «ساخت رزرو» باید فرم رزرو را با نام، تلفن، تاریخ‌ها، تعداد مهمان و یادداشت Pre-fill کند.
- صرف تغییر status مورد لیست انتظار به `converted` بدون ساخت رزرو ممنوع است.
- status فقط پس از ثبت موفق رزرو و در همان Transaction به `converted` تغییر می‌کند.
- «بستن» یک Action مستقل برای مواردی است که دیگر پیگیری نمی‌شوند.

## ۷. پرونده رزرو و ارتباط با مهمان

- پرونده رزرو در موبایل باید اطلاعات و ارتباط ضروری را پیش از عملیات مالی طولانی در دسترس بگذارد.
- اطلاعات تکراری بین Header، Hero و Metadata حذف/فشرده می‌شوند؛ Hero مسئول وضعیت، مهمان، اقامت و شماره رزرو است.
- شماره رزرو برای کار روزانه با الگوی انسانی `YY-MM-####` نمایش داده می‌شود و کدهای Legacy فقط برای سوابق قدیمی حفظ می‌شوند.
- «پیام آزاد» یک Action واقعی است، نه Label/ghost؛ کانال‌های تماس، پیامک، واتس‌اپ و کپی شماره Touch Target یکسان دارند.
- پیام‌های دیگر فقط بر اساس Stage رزرو نمایش داده می‌شوند تا کاربر با «پایان اقامت» یا «لغو رزرو» نامرتبط روبه‌رو نشود.

## ۸. Componentهای مشترک و Production parity

- هر Markup تکرارشونده مانند `info-list` و `service-timeline` باید Component CSS واقعی داشته باشد؛ HTML خام بدون Owner بصری ممنوع است.
- Browser Contract باید همان Dependency Chain واقعی Production را استفاده کند. Test حق ندارد با Inject کردن CSS/Token، Asset ناقص Production را پنهان کند.
- Voucher به‌صورت صریح `tokens.css` را پیش از `voucher.css` Load می‌کند؛ وابستگی مخفی با `@import` در Voucher ممنوع است.
- Touch Target کنترل‌های موبایل حداقل از Token مشترک پروژه پیروی می‌کند و ظاهر Compact نباید Hit Area را قربانی کند.

## ۹. حذف تکرار و Microcopy عملیاتی

- یک داده در یک محدوده دید نباید بدون دلیل دوبار نمایش داده شود؛ Header، Hero، KPI و Panel هرکدام Owner مشخص دارند.
- مسیرهای اصلی Navigation در صفحه «امروز» به شکل Quick Action تکرار نمی‌شوند مگر Action وابسته به Context همان روز باشد.
- عنوان صفحه نباید بلافاصله با همان نام/وضعیت در Card بعدی تکرار شود؛ مثال: پرونده مهمان عنوان عمومی دارد و نام/وضعیت در Overview مالک آن است.
- توضیح زیر عنوان فقط وقتی باقی می‌ماند که تصمیم، محدودیت یا اقدام بعدی را روشن کند؛ بازگویی عنوان با واژه‌های دیگر حذف می‌شود.
- متن‌های معماری و توضیحاتی که فقط برای گفت‌وگوی توسعه معنا دارند وارد UI روزمره نمی‌شوند. جزئیات فنی فقط در بخش‌های مدیریتی/Progressive Disclosure باقی می‌مانند.
- حذف Microcopy نباید هشدار مالی، امنیتی، عملیات مخرب، محدودیت دسترسی یا راه اقدام در Empty/Error State را از بین ببرد.

## ۱۰. صفحه «امروز» به‌عنوان میز کار شیفت

- صفحه «امروز» باید در چند ثانیه وضعیت عملیاتی همان روز را روشن کند؛ KPI مدیریتی بلندمدت جای آن نیست.
- مانده حساب رزروهایی که خروج نهایی آن‌ها امروز است باید در «نیازمند توجه» دیده شود تا مهمان با بدهی بدون پیگیری از اقامتگاه خارج نشود؛ پایان یک اتاق در رزرو چنداتاقه به‌تنهایی «خروج نهایی» محسوب نمی‌شود. Ledger همچنان Owner مبلغ و مانده است و صفحه «امروز» فقط هشدار عملیاتی می‌دهد.
- تعداد «مهمان حاضر» نفر است، اما فهرست اقامت جاری تعداد رزرو/اقامت را نشان می‌دهد؛ عنوان‌ها باید این تفاوت واحد را روشن کنند و عدد رزرو به‌عنوان تعداد مهمان معرفی نشود.
- Hold نزدیک ورود در «نیازمند توجه» باقی می‌ماند، اما Hold امروز و Holdی که موعد ورودش گذشته با متن متفاوت نمایش داده می‌شوند تا اقدام لازم مبهم نباشد.
- «چند روز آینده» باید رزرو قطعی را از Hold جدا نشان دهد؛ Hold ظرفیت را درگیر می‌کند ولی نباید به‌صورت ورود قطعی نمایش داده شود.
- صفحه «امروز» جای ADR، RevPAR، نمودار درآمد، Channel KPI یا Dashboard مدیریتی سنگین نیست؛ این داده‌ها فقط در گزارش یا قابلیت مدیریتیِ واقعاً موردنیاز قرار می‌گیرند.

## ۱۱. یکپارچگی چرخه رزرو و سابقه

- `hold` مرحله پیش از قطعی‌شدن رزرو است. رزرو `confirmed` که تاریخ شروع اقامتش رسیده یا گذشته است، از فرم ویرایش به `hold` برنمی‌گردد؛ اگر نیاز به خاتمه یا اصلاح وضعیت باشد از Action مشخص لغو/عدم مراجعه استفاده می‌شود.
- رزرو پایان‌یافته سابقه عملیاتی و مالی است. ویرایش اتاق/تاریخ/مبلغ اقامت، تغییر تخفیف یا لغو پس از پایان اقامت فقط برای مدیر و با ثبت دلیل مجاز است.
- وصول بدهی یا ثبت بازپرداخت معتبر پس از پایان اقامت، چون با تراکنش جدید و Audit انجام می‌شود، از قاعده ممنوعیت بازنویسی سابقه جداست.
- محدودیت‌های تاریخی باید در Backend enforce شوند؛ مخفی‌کردن دکمه در UI به‌تنهایی کافی نیست.

## ۱۲. مهمانان و پرونده مهمان

- صفحه مهمان CRM نیست؛ هدف آن دسترسی سریع به هویت، تماس، اقامت جاری/آینده، سابقه و یادداشت پایدار است.
- «بازگشتی» فقط بر پایه اقامت تکمیل‌شده تعریف می‌شود؛ رزرو لغوشده یا Hold به‌تنهایی مهمان را بازگشتی نمی‌کند.
- KPI Cardهای مدیریتی، Lifetime Value، Loyalty و Segmentation در این صفحه وارد نمی‌شوند مگر نیاز عملیاتی واقعی اثبات شود.
- یادداشت مهمان مربوط به خود شخص و اقامت‌های بعدی است؛ یادداشت رزرو همچنان متعلق به همان پرونده رزرو باقی می‌ماند.
- Merge پرونده مشابه باید داده را حفظ کند؛ حذف Source بدون انتقال اطلاعات تکمیلی مجاز نیست.

## ۱۳. مرزهای محصولی قفل‌شده در مقیاس فعلی

تا زمانی که نیاز عملیاتی جدید اثبات و با Review تیمی ثبت نشود:

- سامانه Multi-property نمی‌شود؛
- Workflow کامل Check-in/Check-out ساخته نمی‌شود و No-show Exception مینیمال باقی می‌ماند؛
- Housekeeping state machine و Task board سازمانی ساخته نمی‌شود؛
- Channel Manager / OTA Sync خارج Scope فعلی است؛
- «منبع رزرو» Requirement فعلی ندارد و بازگردانده نمی‌شود؛
- Min Stay و Stop Sell به دلیل مدل فعلی ثبت دستی رزروها وارد محصول نمی‌شوند؛
- تعطیل رسمی/جمعه Availability را Block نمی‌کند؛
- قابلیت CRM/Loyalty/Revenue Management صرفاً به دلیل وجود در PMSهای بزرگ اضافه نمی‌شود.

مرجع تصمیم‌گیری و Research: `docs/PROJECT_GOVERNANCE_RND_DESIGN_STANDARD_FA.md`.

## ۱۴. Microcopy و عنوان‌های غیرتکراری در Workspaceهای جدید

- Breadcrumb فقط مسیر را می‌گوید؛ Heading مالک نام کار جاری است؛ Badge فقط وضعیت را نشان می‌دهد. استفاده از هر سه برای تکرار یک مفهوم ممنوع است.
- در Create/Edit اتاق، «افزودن اتاق» یک Owner دارد و Label/Badge «اتاق جدید» کنار آن تکرار نمی‌شود.
- Catalog امکانات از انتخاب امکانات یک اتاق جداست: اپراتور در اتاق فقط Association را انتخاب می‌کند و ویرایش خود Catalog در Settings انجام می‌شود.
- عبارت‌های هم‌معنی مثل «امکانات»، «امکانات مشترک» و «قابلیت‌های اختیاری» باید Domain دقیق داشته باشند تا کاربر تفاوت Catalog اتاق/اقامتگاه با Feature Toggle سامانه را بفهمد.
- کشف تکرار معنی در یک صفحه، Audit backward روی تمام صفحات طراحی‌شده را فعال می‌کند.
